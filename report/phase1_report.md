# Failure Propagation and Recovery in Multi-Agent Workflows — Phase 1

## Goal and setup

Option 5 asks whether tracking dependencies between agent results supports efficient recovery while keeping task execution correct and safe. Phase 1 builds the workload, the fault-injection harness, and the instrumentation, and measures how faults propagate and what the conservative baselines (full restart and always-verify) cost. Phase 2 will add dependency-aware selective invalidation on top of the same traces. Because a workflow we define ourselves is easy to overfit, we also run fault and recovery experiments using Sierra's tau-bench retail harness and a LangGraph implementation of our pipeline (this was feedback used from professor's review of my initial project plan).

**Workflow.** A researcher -> planner -> executor pipeline runs over a deterministic simulated order-fulfillment environment. Only the researcher reads the world and turns it into a fact sheet. The planner sees that sheet and an allocation calculator over it (not the live DB). The executor sees only the plan and issues tool calls. All three agents are `qwen2.5:7b-instruct` on a laptop through Ollama (temperature 0), exchanging JSON. There are 25 tasks in 9 categories (splits, infeasible orders, excluded or closed warehouses, distractors, partial shipments). A run succeeds if and only if the order is fulfilled exactly (or correctly marked infeasible) with no unauthorized action, constraint violation, foreign-order change, or dangling reservation. Each artifact records `depends_on` edges, the world keys it read and their versions, and which facts each plan action used. Reservations are reversible, whereas shipments, emails, and refunds are not.

## Benchmarks

The main experiment is end to end (1,880 + 375 runs). Fifteen fault types are injected, each at one stage. They include inflated or deflated stock, a wrong order quantity, an irrelevant corruption, planner and executor slips, stale reads, timeouts, a customer-note injection, and compromised agents (plus three subtler attacks that ask only for authorized-looking actions). Every task gets the same schedule under `no_recovery`, `restart_snapshot`, `restart_compensate`, `verify_rule`, and `verify_llm`. A clean run is the counterfactual. Propagation is a funnel from "the next agent consumed the fault" down to "the outcome changed." Latency is estimated from tokens (745 prompt / 24 generated tok/s).

The recovery study also uses an existing benchmark and orchestration framework. On tau-bench retail we keep Sierra's database, tools, wiki, and hash-based reward, and wrap the tools with our action log. A 7B `ToolCallingAgent` does not solve these tasks (0/17 on a partial sweep), so the original recovery table uses a ground-truth replay agent on that environment. Replay does not base its actions on read results; its unchanged actions under corrupt reads and malicious notes cannot establish robustness. It is a state-recovery control. A separate LLM supplement below addresses this limitation. Separately, we rebuilt the pipeline in LangGraph and used its `MemorySaver` checkpoints as the framework's idea of recovery. Microbenchmarks time the pieces recovery is built from and scale them well past the real workload.

## External-agent supplement (October 31)

To test propagation through an existing agent rather than predetermined replay actions, we use tau-bench's unchanged `ToolCallingAgent` with the local 7B model on a fixed cohort of retail tasks 17, 48, and 53 (one address change and two returns). These tasks were selected by task type before observing the supplement's clean outcomes. The ordinary observation protocol scores 0/3. A separately labeled grounded variant scores 3/3: at reset, the harness reads the known customer's record and all their orders through the same tool, injection, and verification hooks, then supplies those records as untrusted context. No ground-truth actions or expected answers are given to the model. This removes customer-record discovery as a bottleneck and changes the observation protocol; the resulting score is not an unmodified tau-bench benchmark score or a representative performance estimate.

The grounded fault study pairs all three tasks with `corrupt_read`, `wrong_args`, and persistent `injection`, under no recovery, snapshot restart, compensation restart, and rule verification. The step budget is 16 per attempt in every condition. The fixed cohort is retained even if a clean task fails, and analysis also reports clean-success strata. Each trace records model inputs and responses, tool observations and actions, and conservative dependencies on all prior tool events. Exposure means a faulty observation appeared in a later model prompt; changes in actions and outcomes are measured separately. The injected note's own database change is excluded from a separate agent-caused state metric. The rule verifier checks successful write responses as well as read responses, because either can carry the persistent malicious note.

## Results

**Timing definitions.** The report distinguishes observed harness elapsed time (`wall_s`), accounted stage service time (`latency_s`, which reuses original measured model times on cache hits and includes simulated timeout charges), and token-throughput estimates. Cache reuse means these are not interchangeable. The main report's latency comparisons use estimates unless identified otherwise; the new external-agent summary reports all three separately. Timeout faults are simulated, not actual process kills. Restart cost includes the failed attempt and the rerun; equal step limits apply per attempt rather than equal total inference consumption.

**Clean baseline.** Success is 0.96 (24/25 tasks) at 3 LLM calls and about 2.4k tokens. Accounted stage service time averages 102 seconds; the token-throughput estimate is 28 seconds. The one failure is a natural researcher error. It reported dock = 6 instead of 1, so the order was over-shipped. Always verifying costs little with the rule verifier (9.5 extra reads, no extra inference). Its single clean-run "detection" is that natural error, which it turned into a safe abort. The LLM verifier roughly doubles the cost (6.1 calls, 224 seconds accounted service time; 64 seconds estimated), flags 16% of uninjected runs, and reaches clean success 0.84. That 16% is a clean-run detection rate, not an adjudicated false-positive rate: uninjected runs can contain natural model errors. True false positives have not been independently labeled, so their rate is unknown.

**Propagation.** Relevant faults changed the outcome 59% of the time. Irrelevant ones changed it 0% of the time, and changed a downstream artifact in only 2% of runs. Researcher faults are partly absorbed (38% change the outcome); the planner often reroutes around deflated stock. Planner faults change the outcome 60% of the time, and executor faults 83%. Timeouts are the most damaging (85%) because the orchestrator fails open. Stale fact sheets are not visible in the artifact itself, yet the actions they cause fail against the changed world 91% of the time. That is a shared-state dependency that comparing artifacts cannot see, but the recorded read versions can. Under artifact-level dependencies, every completed downstream stage looks wasted once a researcher fault is revealed (3.0 stages), but only 1.87 stages actually differ from the clean run. That gap is what Phase 2 can try to recover.

**Adversarial.** Success under the original attacks is 0.97 with zero unauthorized actions; the 7B executor refused every privileged call. The scripted pipeline, which trusts every upstream artifact, executes those same actions 100% of the time. In this custom workflow, the observed leak was the upsell injection ("ship 2 extra units, pre-approved"), which changed 16% of plans and caused over-shipments (success 0.88).

**Full restart** looks good when judged on the database (0.92 snapshot, 0.85 compensate) and much worse when judged strictly. Faulted runs had already executed 1.67 irreversible actions on average before recovery. Snapshot restore erased those effects from the DB in 74% of runs, in reality the goods would ship twice, and lost a concurrent external update in 20%. Strict recovery is 0.25. Compensate and rerun keeps reality consistent (strict 0.67), limited by damage that cannot be undone, such as over-shipments. Both variants recompute all 3 stages and discard 0.51 upstream stages that were still valid.

**Always-verify.** The rule verifier caught 100% of the outcome-changing faults and reached 0.96 success at about 1.3× clean cost. It is an upper bound: it reads the live world and checks a hand-written spec. The LLM verifier caught only 54% (46% missed-harmful-fault rate), scored 0.56 overall, and turned a harmless persistent injection into an abort (success 0.28).

On tau-bench (2,592 replay runs, 108 tasks with a ground-truth write) the domain is returns and exchanges, but the recovery story is familiar. Replay solves 78/115 clean tasks (0.68); the misses are multi-turn policy and required prose, not missing tools. The only fault that changes the outcome is an executor slip (`wrong_args`): success 0.12, irreversible deviations in 67% of those runs. Snapshot restore gets success back to 0.70, but strict recovery is 0.05 because it erases about 1.3 irreversible writes. Compensation keeps those writes (strict 0.49) and cannot take back a bad exchange. The rule verifier caught every outcome-changing fault.

LangGraph on our 25 tasks (1,333 scripted runs) isolates a different kind of state. Clean success is 1.00 with about 5 checkpoints per run. Rewinding to the checkpoint before the faulty node restores agent memory and resumes, but leaves the shared world alone (success 0.62, strict 0.52, leftover shipments). Undo our reversible actions first and those numbers become 0.79 and 0.62, and the rerun keeps 0.48 stages a full restart would throw away. A checkpoint is not a database restore.

The microbenchmarks are a check that bookkeeping will not dominate inference. Recording is about 2.3 µs per artifact. Finding everything downstream of a fault in a 10k-artifact graph takes 2.4 ms (the first lookup was quadratic; this is how we noticed). Snapshot restore is milliseconds. Compensation is microseconds per action. A rule check is 9–18 µs; an LLM check is about 12.7 s, more than one of our stages (7–10 s).

## Implications for Phase 2

Irreversible actions, not recomputation, are what limit recovery, so selective recovery has to prefer compensation and say what it cannot undo. Staleness needs key-version checks, not only artifact provenance. Artifact-level invalidation over-invalidates (3.0 stages vs. 1.87 actually affected); field-level provenance is already recorded so we can measure that trade-off. It also matters which state is restored; LangGraph keeps agent memory and loses the database, and a snapshot does the opposite. Phase 2 should treat those as different problems, and should try a workflow with independent branches, since a straight chain has very little work that is safe to keep. Limitations include one seed at temperature 0, one 7B model, 25 custom tasks, an oracle that names the faulty stage, and replay for the broad tau-bench recovery table. The additional real-agent study uses only three preselected retail tasks with an adapted grounding protocol. LangGraph tests an existing framework, but retains our workflow and scripted agents; it is not an independent agent workload.

Restoring state is not just copying a Python dict, which is why Phase 2b is longer. We already measure two ways of handling the **shared database**: snapshot rollback, and compensating our own reversible writes. Snapshot is wrong when something irreversible has already happened or when someone else updated the world in the meantime. Compensation cannot undo a shipment, an email, a refund, or a tau-bench exchange. Selective recovery will have to report those as uncompensable instead of pretending the world was rewound.

**Agent memory** is a different object: conversation history, scratchpads, caches. LangGraph's `MemorySaver` can already rewind the graph to the node before the fault. That is necessary and not enough, because the world stays dirty. In Phase 2 we want to version memory the same way we version artifacts — drop only the messages that depended on the bad result, keep the rest, and check that what we kept is still valid against current key versions.

A **process** mid-flight (a tool that has written a partial file, a reservation that is half applied) cannot be restored by `deepcopy`. The plan is to isolate long tools, log when they start and finish, and on recovery either abort them or resume from a real process checkpoint (CRIU or `docker checkpoint` as an optional comparison). 
**Network** side effects are the same problem as shipments: the request already left. We will use a recording proxy and idempotency keys so retries are safe, issue a compensating call when the service allows it, and otherwise list the effect as irreversible. We will not roll the database back and call that undoing an email.
